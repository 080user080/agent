# Етап 1. Продуктове дослідження — детальний покроковий розбір

> Мета етапу: до написання першого рядка коду має бути зрозуміло, **що саме будується, для кого і навіщо**. Результат — файл `docs/PRD.md`.

**Важливо:** виконуй цей етап в окремому чаті з Cline, **без режиму запису файлів** (Plan mode / без Act mode). Це не дає агенту почати писати код замість того, щоб думати разом з тобою.

---

## Крок 1. Опис проблеми

Перше запитання — не «що робимо», а **«яку проблему вирішуємо»**.

Промпт для Cline:
```
Допоможи мені сформулювати проблему для нового продукту.
Онови docs/PRD.md, розділ "1. Опис проблеми".
Постав мені запитання, якщо чогось не вистачає:
- Яка проблема існує зараз?
- Хто від неї страждає?
- Чому існуюче рішення незручне?
- Чому взагалі потрібна нова програма?
Не пиши код, лише текст у PRD.md.
```

**Критерій готовності кроку:** проблему можна пояснити одним абзацом людині, яка ніколи не бачила проєкту.

---

## Крок 2. Ціль продукту

Одне-два речення, без деталей реалізації. Лише кінцевий результат.

Приклад формулювання:
> «Створити програму, яка автоматично аналізує фотографії та застосовує необхідну обробку без втручання оператора.»

Перевірка: якщо в реченні є слова «база даних», «інтерфейс», «алгоритм» — це вже реалізація, а не ціль. Прибери такі деталі.

---

## Крок 3. Цільовий користувач

Ніколи не «будь-хто». Розділяй на:

- **Основний користувач** — той, хто працює з продуктом щодня.
- **Другорядні користувачі** — ті, кому продукт потрібен рідше або опосередковано (адміністратор, власник бізнесу, спостерігач).

Промпт:
```
Онови розділ "3. Цільові користувачі" у PRD.md.
Постав мені уточнюючі запитання про:
- хто буде основним користувачем щодня
- чи є другорядні ролі (адмін, власник, гість)
- який рівень технічної підготовки в кожної ролі
```

---

## Крок 4. User Stories (сценарії використання)

Формат — рольова історія, **не функція**:

```
Як <роль>
Я хочу <дія>
Щоб <результат>.
```

Практика:
- Пиши 10–20 історій, не менше.
- Одна історія = одна дія, без «і» посередині (якщо є «і» — це дві історії).
- Кожна історія має відповідати на «навіщо», а не тільки «що».

Приклад:
```
Як оператор
Я хочу вибрати папку із фотографіями
Щоб програма автоматично їх обробила.

Як оператор
Я хочу бачити журнал помилок
Щоб швидко знайти проблемне фото.
```

Промпт для Cline:
```
Згенеруй 15-20 чернеток User Stories на основі проблеми та цільових
користувачів з PRD.md. Онови розділ "4. User Stories".
Групуй за ролями. Не переходь до функцій — лише історії.
```

---

## Крок 5. Витягнути функції з User Stories

Кожна User Story перетворюється на одну або кілька конкретних функцій.

```
User Story:  "Вибрати папку"          →  Функція: вибір папки
User Story:  "Переглянути журнал"     →  Функція: журнал обробки
```

Промпт:
```
Пройдись по кожній User Story з розділу 4 і випиши відповідну функцію
у розділ "5. Основні функції". Якщо історія покриває кілька функцій —
розбий явно.
```

---

## Крок 6. Пріоритизація функцій (MoSCoW)

Розділи всі функції на три категорії:

| Категорія | Значення | Приклад |
|---|---|---|
| **Must Have** | без цього продукт не має сенсу | вибір папки, аналіз фото, обробка, збереження |
| **Should Have** | дуже бажано, але не критично для запуску | журнал, пакетна обробка, налаштування |
| **Nice to Have** | можна зробити пізніше | темна тема, автооновлення, хмарна синхронізація |

Порада: якщо сумніваєшся, куди віднести функцію — постав тест «продукт без неї взагалі можна використовувати?». Якщо так — це не Must Have.

---

## Крок 7. Аналіз аналогів (опційно)

Потрібен лише якщо на ринку вже є подібні рішення.

```
| Програма | Що хорошого    | Що поганого        |
|----------|----------------|---------------------|
| A        | швидка         | складний інтерфейс  |
| B        | багато функцій | повільна            |
| C        | проста         | мало можливостей    |
```

Завершуй висновком: що саме береш від кожного аналога.
> «Варто взяти простоту інтерфейсу від A і швидкість роботи від B.»

Якщо аналогів немає або продукт вузькоспеціалізований (внутрішній інструмент) — пропускай крок і зазнач це прямо в PRD: «Аналоги не аналізувались, продукт вузькоспеціалізований».

---

## Крок 8. Уточнюючі питання по категоріях

Тільки після кроків 1–7 Cline має ставити технічні уточнюючі питання. Не хаотично, а блоками:

**Платформа**
- Windows / Linux / Android / Web?

**Дані**
- SQLite / JSON / PostgreSQL / без БД?

**Інтерфейс**
- Tkinter / PySide6 / CLI / веб-інтерфейс?

**Користувач**
- один користувач чи багато (потрібна авторизація)?

**Продуктивність**
- скільки файлів/записів обробляється одночасно?
- які розміри даних?
- чи потрібна багатопоточність?

**Інтернет**
- офлайн чи потрібне підключення?

**Інтеграції**
- зовнішні API, Telegram, Excel, принтер, камера?

Промпт:
```
Задай мені по черзі уточнюючі запитання із категорій: платформа, дані,
інтерфейс, користувач, продуктивність, інтернет, інтеграції.
Одна категорія за раз, не всі одразу.
```

---

## Крок 9. Обмеження

Фіксуй усе, що звужує рамки проєкту й вплине на архітектуру:

- лише Windows;
- Python 3.11+;
- лише CPU (без GPU);
- без Інтернету;
- максимум N файлів за один запуск.

Ці обмеження підуть напряму в `docs/project_rules.md` на наступному етапі.

---

## Крок 10. MVP

Чесно відповісти:
> Який мінімальний набір функцій робить продукт корисним хоч комусь?

Правило: у MVP потрапляють **тільки Must Have**. Should Have і Nice to Have — у Backlog (пункт 12).

---

## Крок 11. Критерії успіху

Формулюй вимірювано, там де можливо:

- оператор може обробити папку без ручного втручання;
- обробка 100 фотографій займає не більше 5 хвилин;
- помилки записуються в журнал;
- програма працює без Інтернету.

Якщо критерій не можна перевірити («програма зручна») — перефразуй так, щоб можна було: «оператор виконує задачу за N кліків».

---

## Крок 12. Фінальна структура docs/PRD.md

```text
1. Опис проблеми
2. Мета продукту
3. Цільові користувачі
4. User Stories
5. Основні функції
6. Must Have / Should Have / Nice to Have
7. Аналоги (за потреби)
8. Обмеження
9. Нефункціональні вимоги
   - швидкодія
   - безпека
   - сумісність
   - надійність
10. MVP
11. Критерії успіху
12. Відкладені ідеї (Backlog)
13. Що НЕ входить у першу версію (Out of Scope)
```

---

## Крок 13. Out of Scope — окремо і явно

Найчастіше пропускають саме цей пункт, а він захищає від «розповзання» проєкту. Приклад:

- немає синхронізації через хмару;
- немає мобільної версії;
- немає підтримки мережевої роботи;
- немає плагінів користувача.

Коли під час розробки з'являється нова ідея — звіряй її з цим списком: реалізувати зараз чи в Backlog.

## Фінальний чек-лист перед переходом до Етапу 2

- [ ] Проблема формулюється одним абзацом
- [ ] Ціль — 1-2 речення без деталей реалізації
- [ ] Є основний і другорядні користувачі
- [ ] 10-20 User Stories, згруповані за ролями
- [ ] Кожна функція виведена з конкретної User Story
- [ ] Функції розподілені по Must/Should/Nice
- [ ] Технічні уточнення (платформа, дані, інтерфейс) зафіксовані
- [ ] Обмеження явно прописані
- [ ] MVP = тільки Must Have
- [ ] Критерії успіху вимірювані
- [ ] Out of Scope прописаний окремо

Якщо всі пункти закриті — `docs/PRD.md` готовий, і можна переходити до Етапу 2 (`project_rules.md`, `architecture.md`, `adr.md`).
