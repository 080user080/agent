# Єдина система розробки проєкту з ШІ-агентом (Cline у VS Code)

Ця система перетворює Cline з «генератора випадкового коду» на керованого виконавця, який працює за чіткою специфікацією, а не фантазує на ходу.

## Загальний пайплайн

```
Ідея / гіпотеза
    │
    ▼
[0. Підготовка середовища]   → структура папок, venv, git, .env
    │
    ▼
[1. Продуктове дослідження]  → docs/PRD.md (що будуємо і навіщо)
    │
    ▼
[2. Інженерне проєктування]  → project_rules.md, architecture.md, adr.md
    │
    ▼
[3. Декомпозиція на завдання] → TASK.md (з критеріями "готово")
    │
    ▼
[4. Ізольована реалізація]   → цикл: написав → протестував → закомітив
    │
    ▼
[5. Інтеграція та фіналізація] → main.py, README.md, CHANGELOG.md
```

Cline не переходить до наступного етапу, поки попередній не затверджено.

---

## Структура папки проєкту

```
my_project/
├── docs/
│   ├── PRD.md              # навіщо і для кого (продукт)
│   ├── project_rules.md    # "конституція" для Cline
│   ├── architecture.md     # як саме технічно (модулі, дані)
│   ├── adr.md               # журнал архітектурних рішень
│   ├── summary.md           # короткий "стан проєкту" (оновлюється періодично)
│   └── CHANGELOG.md
├── src/
├── tests/
├── TASK.md
├── README.md
├── requirements.txt
├── .env                     # секрети, НЕ в git
├── .gitignore
└── venv/
```

`.gitignore` обов'язково включає `venv/`, `.env`, `__pycache__/`.

---

## Етап 0. Підготовка середовища

```bash
mkdir my_project && cd my_project
python -m venv venv
git init
```

Створити порожні `docs/PRD.md`, `docs/project_rules.md`, `docs/architecture.md`, `docs/adr.md`, `TASK.md`, `.gitignore`, `.env`.

---

## Етап 1. Продуктове дослідження → docs/PRD.md

Роль Cline: аналітик. Використовуй окремий чат (без режиму запису файлів), щоб він не почав одразу писати код.

1. Аналіз ринку/аналогів (якщо потрібно) — must-have vs nice-to-have фічі.
2. Уточнюючі запитання: платформа, зберігання даних, цільовий користувач.
3. Фіксація в PRD.md: проблема, user stories, вимоги, MVP-набір фіч.

---

## Етап 2. Інженерне проєктування (без коду)

### 2.1 docs/project_rules.md — конституція

```markdown
# Правила роботи агента

- Платформа: Windows
- Python: 3.11
- Стиль коду: PEP8, type hints, docstrings
- НІКОЛИ не хардкодити секрети/ключі — тільки через .env
- НЕ змінювати architecture.md без явного погодження
- Оновлювати TASK.md одразу після виконання пункту
- НЕ писати код, якщо не отримано прямого завдання з TASK.md
- Кожен завершений модуль — окремий git-комміт з message = "TASK-<номер>: <опис>"
- Раз на 5 виконаних завдань — оновити docs/summary.md коротким підсумком
  поточного стану (щоб не тримати в контексті весь architecture.md)
```

### 2.2 docs/architecture.md — технічна специфікація

- Модулі та їх відповідальність
- Взаємодія між модулями (інтерфейси, потоки даних)
- Технологія зберігання даних, ключові бібліотеки
- Текстова діаграма компонентів
- Відомі обмеження/компроміси

### 2.3 docs/adr.md — журнал рішень

Оновлюється щоразу, коли є відхилення від плану:

```markdown
## ADR-001: Вибір SQLite замість PostgreSQL
Дата: ...
Причина: локальний застосунок, не потребує клієнт-серверної БД.
```

---

## Етап 3. Декомпозиція → TASK.md

Кожен пункт — атомарне завдання **з критерієм "готово"**, інакше Cline сам вирішує, де зупинитись:

```markdown
- [ ] TASK-1. Створити src/storage.py (SQLite-шар збереження)
      Готово, коли: модуль зберігає/читає запис без помилок;
      є if __name__ == '__main__' з тестовим прикладом.
- [ ] TASK-2. Створити src/habits.py (логіка звичок)
      Готово, коли: пройдено 3 сценарії з PRD (додати/оновити/видалити звичку).
- [ ] TASK-3. Створити src/ui.py (консольний інтерфейс)
- [ ] TASK-4. Інтегрувати модулі в main.py
```

---

## Етап 4. Ізольована реалізація (цикл написав → перевірив → закомітив)

Шаблон промпту для Cline:

```
Прочитай docs/project_rules.md та docs/architecture.md.
Виконай TASK-1 з TASK.md — створи src/storage.py.
Додай блок if __name__ == '__main__' для тестування.
Не змінюй інші файли.
Познач задачу як виконану в TASK.md, коли я підтверджу, що тест пройшов.
```

Після генерації:

1. `python src/storage.py` — перевірити вручну.
2. Якщо є тест — `pytest tests/test_storage.py`.
3. При помилці — скопіювати лог і попросити Cline виправити **в межах цього модуля**.
4. Після успіху — `git add . && git commit -m "TASK-1: storage module"`.
5. Позначити `[x]` у TASK.md, перейти до наступного.

Це дає точку відкату: якщо наступний модуль щось поламає, завжди можна повернутись до останнього робочого коміту.

---

## Етап 5. Інтеграція та фіналізація

- `main.py` об'єднує модулі згідно з architecture.md.
- Заповнити README.md (опис, встановлення, запуск).
- Додати запис у CHANGELOG.md.
- Оновити adr.md, якщо під час інтеграції виникли відхилення.
- Фінальне тестування як єдиного цілого.

---

## Зведена роль файлів

| Файл | Призначення | Коли створюється |
|---|---|---|
| docs/PRD.md | Що будуємо, для кого, вимоги | Етап 1 |
| docs/project_rules.md | Правила роботи Cline | Етап 2 |
| docs/architecture.md | Модулі, зв'язки, потоки даних | Етап 2 |
| docs/adr.md | Журнал рішень | Етап 2, постійно |
| docs/summary.md | Короткий поточний стан (проти "забування" контексту) | З 5-го TASK і далі |
| TASK.md | Задачі з критеріями "готово" | Етап 3 |
| .env | Секрети, не в git | Етап 0 |
| README.md / CHANGELOG.md | Опис і історія змін | Етап 5 |

---

## Чому це працює

- **Розділення "думання" і "писання"** — Cline спершу отримує контекст, потім пише код.
- **Ізоляція модулів + git-коміти** — помилка локалізована, завжди є точка відкату.
- **Критерії "готово"** — Cline не вирішує сам, коли зупинитись.
- **summary.md** — контекст не деградує на великих проєктах.
- **Прозорість рішень** — adr.md пояснює "чому так", навіть через місяць.

Правило, яке я б порадив замість додавання нових файлів:
Кожен новий файл/процес у системі має коштувати менше часу, ніж проблема, яку він вирішує. Якщо за місяць роботи ти жодного разу не відкрив adr.md чи summary.md — це сигнал прибрати його, а не додати ще один.
