# Етап 2. Інженерне проєктування (без коду) — детальний покроковий розбір

> Вхід: готовий `docs/PRD.md` з Етапу 1.
> Мета етапу: перевести «що і навіщо» у «як саме технічно», перш ніж торкатись коду. Результат — три файли: `project_rules.md`, `architecture.md`, `adr.md`.

**Важливо:** цей етап теж варто робити без режиму запису коду — тут агент лише пише специфікації, а не імплементацію.

---

## Крок 1. docs/project_rules.md — «конституція» агента

Це файл, який Cline читає **перед кожним завданням**. У ньому — жорсткі правила, які не залежать від конкретного модуля.

### 1.1 Що обов'язково включити

| Розділ | Навіщо |
|---|---|
| Платформа й версія мови | щоб агент не пропонував несумісні бібліотеки |
| Стиль коду | PEP8, type hints, docstrings — узгоджений вигляд усього коду |
| Робота із секретами | заборона хардкодити ключі — тільки `.env` |
| Правила зміни документів | які файли агент не чіпає без дозволу |
| Правила роботи з TODO.md | оновлювати статус одразу після виконання пункту |
| Правило комітів | один завершений модуль = один коміт з чітким message |
| Правило summary.md | коли й навіщо оновлювати короткий підсумок стану |

### 1.2 Базовий шаблон

```markdown
# Правила роботи агента

- Платформа: Windows
- Python: 3.11
- Стиль коду: PEP8, type hints, docstrings
- НІКОЛИ не хардкодити секрети/ключі — тільки через .env
- НЕ змінювати architecture.md без явного погодження
- Оновлювати TODO.md одразу після виконання пункту
- НЕ писати код, якщо не отримано прямого завдання з TODO.md
- Кожен завершений модуль — окремий git-комміт з message = "TODO-<номер>: <опис>"
- Раз на 5 виконаних завдань — оновити docs/summary.md коротким підсумком
  поточного стану (щоб не тримати в контексті весь architecture.md)
```

### 1.3 Промпт для генерації разом з Cline

```
Прочитай docs/PRD.md. На основі обмежень з розділу "8. Обмеження"
згенеруй чернетку docs/project_rules.md за таким шаблоном:
[встав шаблон вище]
Постав уточнюючі запитання, якщо якогось обмеження (платформа, версія
мови, стиль коду) немає в PRD.md.
Не пиши жодного коду — лише файл правил.
```

### 1.4 Чек-лист готовності

- [ ] Платформа й версія мови зафіксовані
- [ ] Явно прописано, де брати секрети (тільки `.env`)
- [ ] Прописано, які файли не можна змінювати без погодження
- [ ] Прописано формат коміту (`TODO-<номер>: <опис>`)
- [ ] Прописано правило оновлення `summary.md`

## Крок 2. docs/architecture.md — технічна специфікація

Це найважливіший документ Етапу 2: саме сюди Cline буде звертатись перед написанням кожного модуля.

### 2.1 Обов'язкові розділи

**Модулі та їх відповідальність**
Список файлів/пакетів із однією фразою «за що відповідає». Наприклад:
```
src/storage.py   — збереження та читання даних (SQLite-шар)
src/habits.py    — бізнес-логіка звичок (додати/оновити/видалити)
src/ui.py        — консольний інтерфейс користувача
main.py          — точка входу, збирає модулі разом
```

**Взаємодія між модулями**
Хто кого викликає, які дані передаються. Найкраще — у вигляді короткого опису потоку:
```
ui.py  →  habits.py  →  storage.py  →  (SQLite файл)
     запит юзера   бізнес-правила   читання/запис
```

**Технологія зберігання даних + ключові бібліотеки**
Конкретно, без «можливо»:
```
БД: SQLite (файл data/app.db)
Бібліотеки: sqlite3 (стандартна), pydantic (валідація), click (CLI)
```

**Текстова діаграма компонентів**
Не обов'язково справжня діаграма — досить ASCII-схеми:
```
┌─────────┐     ┌──────────┐     ┌───────────┐
│  ui.py  │ ──▶ │ habits.py│ ──▶ │storage.py │ ──▶ SQLite
└─────────┘     └──────────┘     └───────────┘
```

**Відомі обмеження/компроміси**
Чесно фіксуй те, що свідомо спрощено:
```
- Без багатопоточності на MVP — обробка послідовна
- Без міграцій БД — схема фіксована на старті
```

### 2.2 Промпт для генерації

```
Прочитай docs/PRD.md (розділи "5. Основні функції" та "8. Обмеження").
Запропонуй чернетку docs/architecture.md з розділами:
- модулі та їх відповідальність
- взаємодія між модулями
- технологія зберігання даних і ключові бібліотеки
- текстова діаграма компонентів
- відомі обмеження/компроміси
Постав уточнюючі запитання щодо вибору БД/бібліотек, якщо це не
випливає однозначно з PRD.md. Не пиши код — лише специфікацію.
```

### 2.3 Чек-лист готовності

- [ ] Кожен модуль має одну чітку відповідальність (не «і те, і те»)
- [ ] Прописано напрямок викликів між модулями
- [ ] Обрана технологія зберігання даних — конкретна, без варіантів
- [ ] Є хоч проста текстова діаграма
- [ ] Обмеження/компроміси зафіксовані, а не замовчані

## Крок 3. docs/adr.md — журнал архітектурних рішень

ADR (Architecture Decision Record) — це не план, а **історія рішень**. Заповнюється не одразу весь, а поступово — щоразу, коли ти відхиляєшся від початкового плану або обираєш між альтернативами.

### 3.1 Коли додавати запис

- обрано технологію замість іншої (SQLite замість PostgreSQL);
- відмовились від функції, яка була в PRD;
- змінили підхід до архітектури під час розробки;
- будь-яке рішення, яке через місяць буде незрозуміле без пояснення «чому».

### 3.2 Шаблон одного запису

```markdown
## ADR-001: Вибір SQLite замість PostgreSQL
Дата: 2026-07-18
Причина: локальний застосунок, не потребує клієнт-серверної БД.
Альтернативи: PostgreSQL (відхилено — надлишкова складність для одного користувача)
Наслідки: спрощене розгортання, обмеження на конкурентний доступ
```

### 3.3 Промпт для старту файлу

```
Створи docs/adr.md з одним початковим записом ADR-001, що фіксує
вибір технології зберігання даних із docs/architecture.md.
Далі додавай новий запис щоразу, коли я скажу "зафіксуй рішення в adr".
```

### 3.4 Чек-лист готовності

- [ ] Файл створено (навіть якщо поки один запис)
- [ ] Кожен запис має дату, причину, альтернативи, наслідки
- [ ] Записи не переписуються заднім числом — тільки додаються нові

## Порядок дій на Етапі 2 (підсумок)

```
1. project_rules.md   — фіксуємо жорсткі правила (робиться першим,
                         бо architecture.md має їх враховувати)
2. architecture.md    — технічна специфікація на основі PRD.md
3. adr.md             — стартовий запис про ключові технічні рішення
                         з architecture.md
```

## Фінальний чек-лист перед переходом до Етапу 3

- [ ] `project_rules.md` містить платформу, стиль коду, правила секретів, комітів, TODO.md, summary.md
- [ ] `architecture.md` описує всі модулі з PRD, взаємодію, зберігання даних, діаграму, обмеження
- [ ] `adr.md` створений і має хоча б один запис про ключове рішення
- [ ] Жодного рядка коду ще не написано

Коли всі пункти закриті — можна переходити до Етапу 3 (декомпозиція на завдання → `TODO.md`).
